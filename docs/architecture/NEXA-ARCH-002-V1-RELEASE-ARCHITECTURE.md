# NEXA-ARCH-002 — Nexa v1 Release Architecture

Status: Approved v1 architecture; reconciled by ADR-0069
Date: 2026-08-26
Supersedes for v1 implementation: `NEXA-ARCH-001` reconstructed architecture narrative
Preserves: the long-term Nexa tutor mission, accepted ADRs unless explicitly superseded, and the renderer-neutral semantic behavior rule

## 1. Purpose

This architecture is the governing system-level baseline for Nexa v1 work after the 2026-08 tactical pause. It converts the reconstructed broad architecture into a finite first-release architecture and restores the rule that parent architecture must lead lower-level implementation.

`NEXA-ARCH-001` remains preserved as historical/reconstructed design provenance and long-range context. It is no longer the direct implementation authority for choosing the next v1 increment where this architecture is more specific.

## 2. v1 system objective

Nexa v1 is a local-first adaptive tutor in which one learner can:

1. launch a supported desktop application;
2. start or resume a governed lesson;
3. interact through text;
4. receive a grounded tutor response generated by one real configured model path;
5. complete governed practice/assessment;
6. have evidence, mastery, and lesson progress committed durably;
7. exit and restart without losing or duplicating accepted work;
8. receive clear failures and recover safely from expected dependency problems.

The system is accepted by observable learner outcomes, not by the number of implemented contracts or ADRs.

## 3. Architectural invariants

The following remain mandatory:

- Tutor intelligence produces instructional/communicative semantics, not renderer primitives.
- Model output is untrusted until admission and required quality gates succeed.
- Domain policy remains in owning domain crates; applications/adapters do not reimplement it.
- Storage technology does not own domain semantics or replace canonical IDs.
- Provider neutrality is preserved at contract boundaries even though v1 begins with one concrete provider path.
- Local correctness evidence and system/release maturity are tracked separately.
- A lower-level ADR or implementation cannot silently close an unresolved parent architecture/specification gap.

## 4. v1 composition

```text
identical shared frontend
  |-- same-machine browser
  `-- Tauri 2 Windows shell
              |
      versioned loopback HTTP/WebSocket API
              |
        one local Rust runtime
   +----------+-----------+-------------+
   |          |           |             |
 SQLite   governed TCP  LM Studio   bundled speech
 state      content      adapter     + synchronized 2D
```

React/TypeScript/Vite, Tauri 2, and the single versioned same-machine loopback HTTP/WebSocket boundary are selected v1 architecture after the G1 gate. Sherpa-ONNX and Rive remain evidence-gated candidates. The runtime is authoritative for business behavior and state. Tauri commands never form a second business API. Nexa bundles no LLM weights or inference runtime.

## 5. Application boundary

The identical React/TypeScript/Vite shared frontend is the learner-facing boundary in both the same-machine browser and the selected Tauri 2 Windows shell. Both use the single versioned same-machine loopback HTTP/WebSocket business boundary; later implementation must establish the production composition rather than promote the disposable G1 fixture.

It owns:

- window/application lifecycle;
- course/lesson navigation;
- text input and tutor response presentation;
- assessment/practice UI;
- progress/error/recovery presentation;
- configuration of concrete adapters;
- graceful application shutdown.

It MUST NOT own:

- mastery logic;
- pedagogy policy;
- scoring logic;
- retrieval ranking policy;
- prompt authority;
- model-output admission policy;
- persistence domain semantics.

`apps/nexa-headless` remains integration/test infrastructure.

## 6. Session orchestration boundary

The orchestrator owns the complete interaction workflow. For a normal interaction it coordinates:

1. session/workflow validation;
2. authoritative learner/lesson state load;
3. current learning activity/objective resolution;
4. mastery/pedagogy input;
5. governed knowledge retrieval/context assembly;
6. tutor prompt/request construction;
7. concrete model invocation;
8. structural admission and release-quality validation;
9. learner presentation;
10. assessment/practice processing where applicable;
11. atomic durable state commit;
12. correlated content-safe operational evidence.

The orchestrator specification owns timeout, retry, cancellation, shutdown, and recovery sequencing. It coordinates subsystem work but does not absorb subsystem reasoning.

## 7. Learning architecture

The deterministic Phase 3 learning core remains the policy foundation.

For v1, its production boundary requires:

- a durable unit of work;
- optimistic concurrency or stronger conflict protection for supported access patterns;
- explicit authored content/version association;
- replayable immutable evidence;
- restart/resume behavior;
- migration and recovery behavior;
- privacy-driven retention/deletion mechanisms.

One accepted learning operation MUST NOT expose partially committed assessment, evidence, mastery, progress, or receipt state.

## 8. Tutor/model architecture

Existing `nexa-tutor` provider-neutral contracts remain reusable.

The v1 route uses one explicit concrete model adapter and one configured model. The adapter owns:

- local HTTP transport;
- endpoint/process configuration;
- provider-specific request/response mapping;
- concrete tokenization/capacity behavior where required;
- timeout/error normalization;
- adapter-specific version compatibility.

The model never becomes the authority for host IDs, authorization, limits, policy versions, capabilities, tools, or renderer operations.

Dynamic multi-provider routing and fallback are post-v1.

## 9. Knowledge architecture

Existing deterministic ingestion, lexical/vector/hybrid retrieval, context assembly, and citation contracts are retained as reusable foundation.

The v1 route requires only the smallest retrieval configuration that meets the governed first-course quality and performance requirements.

The concrete data path must persist:

- source identity/governance;
- artifact identity/version/hash;
- chunk identity/provenance;
- visibility/exposure state;
- any embeddings/profile data actually required by the selected v1 retrieval configuration.

A dedicated vector database is not required unless measured evidence shows the bounded v1 corpus cannot meet accepted requirements without one.

## 10. Data architecture

SQLite is the first v1 durable store, implemented behind `crates/nexa-storage` through `rusqlite`.

Authoritative v1 state categories include:

- learner identity/profile fields required by v1;
- authored course/lesson version identity;
- lesson progress;
- assessment attempts/results required for progression;
- immutable learning evidence;
- derived mastery/replay metadata;
- knowledge source/artifact/chunk provenance;
- recovery/schema metadata needed for safe startup and migration.

Secrets are stored separately according to security policy.

Canonical Nexa identifiers remain authoritative; database-generated row IDs are implementation details only.

## 11. Event architecture

Typed events remain domain facts and integration evidence.

The v1 route does not require a durable event broker. Durable state correctness is established through the SQLite transaction boundary.

A durable outbox/event store becomes required only when a concrete asynchronous durable consumer is part of the accepted release path and loss of its fact would violate correctness.

Operational telemetry is not automatically authoritative domain state.

## 12. Security and privacy architecture

The v1 route is local-model-first.

Minimum controls:

- local model server bound to loopback by default;
- endpoints/model paths derived from trusted configuration;
- no secrets in normal domain persistence or diagnostics;
- persisted data revalidated at trust boundaries;
- model/knowledge/learner content cannot gain host structural authority;
- least-privilege filesystem/process behavior;
- explicit data retention/deletion mechanics;
- no remote disclosure merely because provider-neutral remote contracts already exist.

Any later remote provider requires explicit privacy/security authorization and transport policy.

## 13. Observability architecture

Every primary interaction is correlated through canonical session/workflow/model and relevant domain identities.

Normal diagnostics may record:

- IDs;
- versions;
- hashes/replay anchors;
- outcome/error classifications;
- timings and counts;
- lifecycle transitions.

Normal diagnostics MUST NOT contain raw learner text, knowledge content, compiled prompts, raw model output, assessment responses, or secrets.

## 14. Owner-approved v1 technology route

ADR-0069 controls direct conflicts with ADR-0068. The v1 route requires both identical clients, one loopback API/WebSocket boundary, SQLite, LM Studio, bundled speech, synchronized animated 2D embodiment, Windows x86_64 validation, and the governed TCP lesson. Candidate frameworks/adapters remain evidence-gated as described above.

## 15. Primary v1 sequence

The primary sequence launches either client, resumes authoritative SQLite state, runs the governed lesson through the shared runtime and LM Studio adapter, admits the untrusted model output, commits assessment/evidence/mastery atomically, produces bundled speech and synchronized semantic 2D behavior, and survives interruption/restart without duplication or loss.

## 16. v1 exit evidence

The route closes only through concrete-adapter integration followed by system verification on both clients, accessibility/privacy/security/performance evidence, Windows packaging/recovery evidence, and owner user acceptance. Contract tests, headless integration, research, or spike code cannot establish those maturities.

## 17. Deferred capabilities

LAN/remote access, hosted deployment, cloud sync, accounts/multi-user administration, labs/tools, broad model-server support, dynamic routing/fallback, dedicated vector infrastructure unless proven necessary, durable event brokerage, and 3D release integration are deferred. Provider-neutral, renderer-neutral, speech, avatar, 3D, and labs foundations remain preserved at their factual maturity.

## 18. Architecture rebaseline rule

After G1–G3 candidate evidence and at every later major release gate, the Chief Systems Architect must perform an independent whole-system review covering:

- parent specification maturity;
- vertical capability progress;
- inherited deferrals;
- architecture/document consistency;
- concrete adapter maturity;
- release blocker trajectory;
- whether the roadmap remains the shortest credible path to the release definition.

The outcome is explicitly Continue, Redirect, or Tactical Pause.

## 19. Relationship to existing authority

- `NEXA-ARCH-001` is preserved as reconstructed design provenance and long-term context but is superseded by this document for v1 implementation selection.
- Accepted ADR-0001 through ADR-0067 remain in force unless a direct conflict exists; ADR-0069 controls conflicts with ADR-0068, while earlier capabilities remain retained at their factual maturity or deferred as recorded.
- Baseline subsystem specifications remain applicable within their owned domains, supplemented by the approved R1 v1 baseline described in `NEXA-R1-IMPLEMENTATION-BASELINE.md`.

## 20. Approval basis

Issue #114 supplied explicit owner review of the v1 delivery decisions recorded in ADR-0069. That review authorizes this reconciled architecture only; it does not delegate open-ended implementation or waive the finite evidence gates.
