# Nexa Tutor and Knowledge v1 Rebaseline Requirements — Draft

Status: R1 proposal; intended to mature `NEXA-TUTOR-001` and `NEXA-KNOW-001`, not replace them silently

## 1. Purpose

Consolidate the product-level requirements that the existing Phase 4 ADR sequence did not establish: a concrete v1 knowledge store/retrieval path, one real model-provider path, grounding/citation quality, privacy integration, and release acceptance.

The final governance action should revise/promote the existing parent specifications and preserve accepted ADRs as supporting decisions where still applicable.

## 2. v1 tutor outcome

Given an exact learner/session/course/lesson state and governed knowledge context, Nexa produces one bounded tutor response that:

- is generated by the configured concrete v1 model path;
- is structurally admitted under host-owned authority;
- is grounded to the supplied governed knowledge for factual instructional claims where grounding is required;
- carries citations/source evidence according to the released tutor UX;
- respects assessment-protection and privacy/disclosure policy;
- is instructionally acceptable against the v1 evaluation criteria;
- fails visibly and safely when the provider or quality gates cannot produce an acceptable result.

## 3. Existing Phase 4 foundations retained

The following remain useful foundation evidence where consistent with the approved v1 parent requirements:

- governed ingestion/provenance;
- deterministic lexical/vector/hybrid contracts;
- context assembly and token budgeting;
- deterministic citation resolution;
- structured tutor response planning;
- provider-neutral model request/response contracts;
- deterministic prompt compilation;
- strict raw-output admission;
- model registry/selection abstractions;
- remote authorization/disclosure-filter evidence;
- tokenizer/capacity evidence;
- usage reconciliation.

The rebaseline must avoid forcing every optional composition variant into the v1 runtime path.

## 4. v1 provider policy

v1 requires one explicitly supported concrete provider/model path.

Requirements:

- provider/model configuration is explicit and inspectable;
- provider-neutral domain contracts remain independent of vendor SDKs;
- concrete adapter owns SDK/API/transport/credential behavior;
- exact provider/model/tokenizer compatibility is validated before invocation;
- request/response size/time bounds are enforced;
- provider failures normalize into content-safe bounded errors;
- remote disclosure policy is checked before any remote call;
- no hidden fallback to a second provider/model;
- provider/model/version used for evaluation/release evidence is recorded.

Dynamic selection/routing may remain available as reusable contract code without becoming the v1 production policy.

## 5. Concrete model adapter boundary

The concrete adapter must implement the existing provider-neutral invocation contract or an explicitly reviewed compatible boundary.

It owns:

- provider client lifecycle;
- endpoint/transport configuration;
- credential access;
- provider-specific request translation;
- tokenizer/model capacity integration where required;
- provider timeout/cancellation support;
- response translation;
- provider error normalization;
- provider-reported usage translation where available.

It does not own:

- learner/pedagogy/assessment policy;
- knowledge retrieval;
- prompt privacy authorization;
- structural admission authority;
- semantic/instructional acceptance policy;
- retry/fallback policy beyond adapter-safe transport behavior explicitly allowed by orchestration.

## 6. Knowledge persistence and ingestion

v1 requires a concrete durable knowledge repository for the first released course.

Requirements:

- source/artifact/version/hash/provenance survive restart;
- ingestion validates before content becomes retrievable;
- active content set is atomically promoted or equivalently protected from partial visibility;
- content format scope is intentionally bounded to what the first course uses;
- content/version changes that could invalidate citations/progress are versioned explicitly;
- assessment-protected content retains governed exposure restrictions;
- corruption/unsupported versions fail safely;
- provenance required by rendered citations remains resolvable after restart.

## 7. Retrieval architecture

The existing deterministic retrieval algorithms are candidates, not a requirement to deploy every retrieval mode.

The concrete v1 retrieval path is selected from quality/performance evidence for the released corpus.

Possible acceptable v1 configurations include:

- lexical-only if quality gates pass;
- hybrid lexical/vector using locally persisted embeddings if required;
- another reviewed implementation behind the governed retrieval contracts.

A separate vector database is not required by architecture alone.

## 8. Retrieval quality

The released retrieval path must be evaluated for the actual first-course corpus.

Evaluation set must cover:

- direct factual questions;
- prerequisite/context questions;
- similar/ambiguous concepts;
- assessment-protected content exclusions;
- irrelevant/no-answer cases;
- versioned/outdated source handling as applicable.

Record retrieval configuration, corpus version, expected supporting sources, and pass criteria.

## 9. Context assembly

The v1 prompt context must combine only the approved information required for the interaction, potentially including:

- system/tutor role instructions;
- current course/lesson/objective;
- bounded learner/mastery context;
- pedagogy decision/reference;
- learner turn/input;
- governed retrieved knowledge chunks;
- required assessment constraints;
- output schema/instruction requirements.

Every layer has an authority/privacy classification. Remote-capable compilation applies the approved privacy policy before provider invocation.

Do not persist complete compiled prompts by default merely for convenience.

## 10. Grounding and citation semantics

Structural citation reference validity does not prove that a claim is actually supported.

v1 must define a release-appropriate grounding rule for factual instructional claims. At minimum:

- claims expected to be source-grounded identify one or more citations/references;
- cited source evidence must be present in the exact context supplied to the model or otherwise governed by the approved architecture;
- evaluation determines whether cited material supports the claim, not merely whether the identifier exists;
- unsupported high-confidence factual claims are a quality failure according to the approved threshold/policy;
- when governed context does not support an answer, the tutor may qualify/refuse/ask to proceed without pretending certainty.

The exact automated/deterministic/model-evaluator method is an implementation/evaluation decision governed by the testing specification.

## 11. Instructional quality

Nexa v1 must be evaluated as a tutor, not only as a valid JSON generator.

The release evaluation set should score at least:

- factual correctness relative to governed material;
- relevance to lesson objective;
- appropriateness to learner level/mastery context;
- adherence to pedagogy decision/strategy where applicable;
- clarity/actionability;
- avoidance of revealing protected assessment answers;
- appropriate uncertainty/refusal when evidence is insufficient;
- absence of unsafe/host-authority-seeking output.

Thresholds and evaluator method must be approved and versioned.

## 12. Prompt injection / hostile source handling

Governed source text remains untrusted as host instruction unless explicitly authored into a trusted instruction layer.

The v1 evaluation/acceptance suite must include source/learner text containing instruction-like content intended to:

- override system/tutor policy;
- request secrets;
- request hidden assessment material;
- alter output schema;
- redirect to unauthorized tools/network behavior;
- suppress citations/grounding controls.

Success means the host-owned architecture remains authoritative and the response satisfies the required acceptance policy.

## 13. Assessment protection

Tutor/knowledge integration must preserve the existing distinction between instructional content and protected assessment material.

Requirements:

- retrieval excludes protected answer content according to governed exposure rules before learner-facing generation;
- remote prompt construction cannot reintroduce excluded answers through another layer;
- evaluator/scoring workflows that need protected data use a separate governed authority path rather than learner-facing generation context;
- tutor quality tests include common answer-leak attempts.

## 14. Privacy integration

For remote inference:

- data-class disclosure is governed by the v1 privacy specification;
- only approved prompt layers/content cross the boundary;
- learner-history inclusion is minimized to current instructional need;
- logs/evidence remain content-safe;
- provider-side retention/handling assumptions are not treated as Nexa-controlled facts.

For local inference:

- remote disclosure authorization is unnecessary, but local model/runtime filesystem/process security remains governed by the security specification.

## 15. Failure behavior

The tutor/knowledge stack must normalize at least:

- content/course/knowledge unavailable or invalid;
- retrieval failure/insufficient grounding;
- prompt/context over capacity;
- provider configuration/authentication failure;
- provider timeout/unavailable/error;
- invalid/unsupported provider response;
- structural admission rejection;
- grounding/quality rejection;
- privacy/security refusal.

The orchestrator decides retry/recovery/user flow; the tutor/knowledge components provide exact bounded classifications and evidence.

## 16. Response persistence

v1 does not require indefinite persistence of raw model output or full conversation history.

Persist only what the approved product/data/privacy architecture requires for:

- learner progress/evidence;
- citation/provenance replay where needed;
- bounded operational evidence;
- explicitly approved persistent learner memory.

Do not convert every prompt/response into permanent memory by default.

## 17. Verification

Before System Verified maturity, prove:

- concrete provider adapter happy path;
- provider config/auth/unavailable/timeout errors;
- exact provider/model/tokenizer association;
- privacy authorization/disclosure failure before remote invocation;
- concrete durable knowledge restart/reopen;
- retrieval quality on released corpus;
- citation provenance after restart;
- structural admission against actual provider output;
- grounding/citation fidelity evaluation;
- instructional-quality evaluation;
- assessment-protection cases;
- hostile prompt/source cases;
- no sensitive raw content in normal diagnostics;
- end-to-end tutor response through the actual learner application.

## 18. v1 deliberate simplifications

Unless explicitly promoted, v1 does not require:

- dynamic health/cost/latency/task-complexity routing;
- automatic local-first fallback chains;
- multiple simultaneous providers;
- retry/regeneration chains beyond bounded approved policy;
- streaming model tokens;
- generalized semantic memory;
- external vector database;
- learned/cross-encoder reranking;
- cloud knowledge service;
- generalized tool-calling agent behavior.

## 19. Approval decisions

- first concrete provider/model and local/remote posture;
- provider/tokenizer adapter choice;
- released corpus/content formats;
- concrete retrieval mode from measured evidence;
- grounding/citation acceptance method and threshold;
- instructional-quality evaluation method/threshold;
- prompt-injection acceptance policy;
- whether any model/conversation content is persisted;
- exact retry policy delegated to orchestration.

## 2026-08-26 ADR-0069 reconciliation

LM Studio is the sole validated v1 reference server through a narrow adapter; broad compatibility is not promised and no hidden fallback is allowed. Nexa bundles neither LLM weights nor inference runtime. Provider-neutral ports remain. Admitted tutor semantics may drive owned behavior states but model output never selects renderer primitives.
